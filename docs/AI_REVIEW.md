# AI-assisted development review

Тестовое задание разрабатывалось с активным использованием ИИ-инструментов. При этом ИИ использовался как ускоритель разработки, а не как источник безусловно корректного результата.

Цель процесса была простой:

```text
сгенерировать гипотезу → проверить → найти расхождения → исправить → добавить regression-test
```

## Что делегировалось ИИ

- декомпозиция исходного задания;
- проектирование сущностей и связей;
- первоначальная архитектура REST API;
- черновые варианты UI;
- генерация части кода;
- генерация тест-кейсов;
- code review;
- анализ найденных во время smoke-test дефектов.

## Что проверялось вручную

Вручную были пройдены основные пользовательские сценарии:

- создание проекта;
- выбор роли и менеджера;
- фиксация выполнения;
- поступления от конкретного плательщика;
- расход на внешнего контрагента;
- расход на сотрудника нужной роли;
- добавление сотрудника в команду;
- создание пользовательской статьи;
- документы;
- Overview;
- периодные фильтры;
- поиск;
- финансовое состояние;
- аналитика сотрудников;
- KPI и drill-down;
- переходы между проектами и детализациями;
- required-поля и disabled submit;
- demo-база за несколько месяцев.

## Что проверяется автоматически

Финальная версия проходит 39 автоматических тестов.

Покрыты в том числе:

- прибыль на основе выполненных работ, а не денежных поступлений;
- накопительная дебиторка;
- аванс клиента;
- периодная сумма сделок;
- точность хранения денег;
- отсутствие умножения финансовых итогов из-за JOIN участников проекта;
- period filters;
- плательщики и контрагенты;
- employee-linked расходы;
- роль сотрудника;
- формы;
- frontend regression-контракты;
- showcase seed.

## Примеры ошибок, найденных во время проверки

### 1. Умножение финансовых сумм из-за JOIN

В ранней версии одновременно соединялись финансовые операции и участники проекта.

При наличии нескольких участников одна операция могла участвовать в агрегате несколько раз.

Исправление:
- финансовые показатели и команда проекта агрегируются независимо;
- добавлен regression-test `multiple members do not duplicate project financial totals`.

### 2. Деньги в `REAL`

Первая версия использовала floating point для денежных значений.

Для финансовых расчётов это нежелательно.

Исправление:
- суммы хранятся как integer-копейки;
- конвертация в рубли выполняется на границе API;
- есть тесты на точность и запрет избыточных знаков после запятой.

### 3. Смешение факта выполнения и денег

Изначально простая модель `Доходы − Расходы` недостаточно хорошо описывала проектную экономику: поступление денег не означает, что соответствующий объём работ уже выполнен.

Финальная модель разделяет:

```text
Сделка
Выполнено
Получено
Расходы
Прибыль
Рентабельность
Дебиторка
```

Прибыль считается от выполненных работ:

```text
Прибыль = Выполнено − Расходы
```

### 4. Дебиторка должна быть накопительной

Периодная разница `Выполнено − Получено` не показывает весь долг клиента по проекту.

Исправление:
- KPI периода остаются периодными;
- общая дебиторка считается накопительно на конец периода;
- аванс отделён от дебиторки;
- добавлены тесты и помесячный drill-down.

### 5. Сумма сделки и период

Внутри проекта договорная сумма должна быть постоянной, но на Overview KPI `Сумма сделок за период` должен учитывать дату сделки.

Исправление:
- карточка проекта хранит и показывает полную сумму;
- периодный Overview считает только сделки с `deal_date` внутри периода;
- добавлен отдельный тест.

### 6. Роль сотрудника в расходной статье

При выборе статьи `Внутренние программисты` первоначально можно было выбрать сотрудника любой роли.

Исправление:
- расходная статья может быть связана с employee role;
- UI показывает только сотрудников этой роли;
- backend повторно проверяет соответствие роли;
- сценарий покрыт тестами.

### 7. Обязательные поля формы

В раннем UI submit-кнопки могли становиться активными до заполнения всех обязательных полей.

Исправление:
- единый validation engine для форм;
- кнопка визуально disabled до валидного состояния;
- backend остаётся второй линией проверки.

### 8. Frontend regression во время итераций

Во время одной из UI-доработок функция `syncProjectManagers()` случайно выпала из frontend-файла. API и база были исправны, но bootstrap SPA останавливался.

Ошибка была локализована через browser console:

```text
ReferenceError: syncProjectManagers is not defined
```

После восстановления функции добавлен regression-test на наличие runtime helpers.

Это хороший пример того, почему успешный backend-test сам по себе не означает, что пользовательский сценарий работает.

### 9. Перерисовка интерфейса ломала ввод

При live search и числовом фильтре компонент перерисовывался на каждый символ:
- строка поиска теряла фокус;
- цифры минимальной рентабельности могли вводиться в неправильном порядке.

Исправление:
- ввод отделён от полной перерисовки;
- добавлены regression-tests на сохранение typing flow.

## Showcase-данные тоже проверяются

Demo seed — воспроизводимый, а не вручную сохранённый SQLite-файл.

Он создаёт:
- 20 проектов;
- 16 сотрудников;
- 5 месяцев истории;
- разные виды операций и документов;
- несколько плательщиков;
- проекты с разным финансовым состоянием.

Отдельный тест запускает seed во временной БД и проверяет согласованность данных.

Во время ручной проверки также было исправлено бизнес-правдоподобие завершённого проекта: после окончания производства он больше не получает новые выполнения и производственные расходы, но может получить финальную оплату ранее сформированной дебиторки.

## Осознанные ограничения

Для тестового задания намеренно не реализованы:
- обязательная OAuth-авторизация Bitrix24;
- полноценная матрица прав;
- автоматическая синхронизация пользователей портала;
- production audit log.

Это не блокирует проверку задания и позволяет запустить проект локально без секретов и внешней инфраструктуры.

Для production следующими шагами были бы OAuth, RBAC, audit log и PostgreSQL при росте нагрузки.

## Вывод

ИИ заметно ускорил разработку, но наиболее важная часть работы была не в генерации кода, а в цикле проверки.

Финансовая логика, периодность, роли, формы и UI неоднократно корректировались после автоматических и ручных проверок. Каждая найденная регрессия по возможности закреплялась тестом, чтобы она не возвращалась в следующих итерациях.
